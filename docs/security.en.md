# Security and anonymity

[← Back to README](../README.en.md) · [简体中文](security.md) | English

**What the operator can see, and what can't be promised.** Plain SSH cannot do end-to-end encryption: SSH's encryption ends at the server, the chat program has to see the plaintext to relay it, and the operator has root on that server. What this project can do is make the program **leave as little behind as possible**, and let users check that for themselves:

- In the chat, `/privacy` shows the data policy of **this server's actual running configuration**: how long messages are kept, whether bans are persisted, whether Tor is on, what admins can do.
- `/forget` immediately removes everything you posted this session from the server's room history.
- Messages live in memory only and expire; no IPs, nicknames or message text in the logs; systemd forbids core dumps (`LimitCORE=0`), so a crash never writes chat contents to disk.
- The code is open and releases are built by GitHub Actions from the public source, with SHA256SUMS. But nobody can verify remotely that a given server runs an unmodified build, so in the end it comes down to whether you trust the operator. **Never post anything that identifies you.** To hide your IP from the operator too, use Tor.

- **SSH encrypts the connection, not end to end.** The server process can read messages; everyone is reminded of this on every visit.
- **No shell.** No exec, SFTP/SCP, port forwarding, agent forwarding or X11. CI verifies this on a real server.
- **No IP logging.** No IPs, nicknames or messages in the logs, and address fields written by third-party libraries are filtered too. Rate limits and bans use an HMAC of the IP whose key lives only in memory and changes on every restart; IPv6 is grouped by /64. The health endpoint returns counts only.
- **Your client never sends a public key.** Normally an SSH client offers every public key on your computer to the server one by one. Everyone's GitHub keys are public, so a server could match them and know who you are. This server accepts ordinary users at the very first SSH authentication step (`none`), before the client gets as far as offering keys. Only the username `admin` goes on to key authentication. Check it with `ssh -v`: you'll see `Authenticated ... using "none"` and no `Offering public key`. CI tests this too.
- **Ban persistence is optional, and has a cost.** By default the key for the address hashes lives only in memory, so nothing on disk can be linked to an address — but bans are forgotten on restart. With `--persist-bans` the key is saved next to the ban list in `/var/lib/vivant/` (mode 0600, readable only by the service); the disk holds only hashes of banned addresses, no IPs and nothing about other users. The risk: someone who gets both files could brute-force the IPv4 space and recover the **banned** addresses. If anonymity matters most, leave it off. Also, when the service starts with no ban still active it switches to a fresh key, so the old key (and any copy of it) is useless against past bans.
- **Messages never touch disk.** Each room keeps the last 500 messages, for at most 24 hours, in memory (private rooms at most 100), and a restart wipes them; private rooms vanish when empty; private messages are not stored at all.
- **Terminal injection protection.** Control characters in nicknames and messages are stripped — and with them every ANSI/OSC/DCS escape sequence, including OSC 52 (clipboard access) and `ESC [6n` (cursor position report) — as are Unicode bidi overrides, invisible characters such as zero-width spaces, and Unicode "tag" characters that can hide a line of invisible text. Zero-width joiners needed by emoji sequences, Persian and Indic scripts are kept. A test walks every code point in the control, format and tag ranges and checks none survives (`cargo test`, run by CI every time).
- **Modern SSH algorithms only.** Key exchange is limited to mlkem768x25519 (post-quantum hybrid), curve25519 and ECDH; SHA-1 and finite-field Diffie-Hellman are gone (the latter costs 2048–4096-bit modular exponentiation before the user even authenticates, the easiest way to burn server CPU). hmac-sha1 is no longer accepted. Every SSH client from the last decade (OpenSSH 6.5+, PuTTY 0.68+, Termius, iSH) supports these.
- **Abuse protection.** Per address: at most 3 sessions, 8 TCP connections and 10 new connections a minute; each connection may send 32 KB/s before it is slowed down (so junk floods can't burn CPU); a message token bucket (burst 5, 1 per second); repeated messages blocked; automatic mute for repeated flooding; disconnect after 1 hour without posting.
- **Handshake timeout and a global connection cap.** Connections that haven't entered the chat within 30 seconds (port scanners, stalled handshakes) are closed instead of holding a slot until the 1-hour idle timeout. The total number of TCP connections is capped too (twice the session limit plus 500), so a flood from many different addresses can't exhaust file descriptors.
- **Design rule: passphrases are asked in the chat, never at SSH authentication.** If a passphrase-protected private instance is ever added, the connection will be accepted with `none` first and the passphrase typed in the chat. The reason: once an SSH server stops accepting `none`, clients start offering every public key on the machine, and the user's identity is exposed. ssh-chat's server password and sshoosh's invite tokens are both asked at authentication; this project doesn't do that.
- **Tor onion service (optional).** On a normal connection the VPS and the cloud provider still see the source IP; that can't be removed at the application level. Install with `--tor` and the chat is also published at a `.onion` address: for users arriving through Tor the server only sees "from Tor", never their real IP. The cost: those users can't be banned by address (`/ban` kicks instead), and they share one set of more generous limits.

## Tor

Connecting with Tor Browser works even if the operator didn't enable the onion service: the server periodically downloads Tor's public exit list, and people arriving through an exit share one set of generous limits instead of being turned away because "this IP already has 3 sessions" (a similar project uses the same list to block Tor users; we do the opposite). Downloading the list involves no user data; operators can turn it off with `VIVANT_TOR_EXITS=off`.

On a normal connection the VPS and the cloud provider can see source IPs. Installing with `--tor` also publishes a `.onion` address, and users connecting through Tor never show their real IP to the server. Setting it up: [Deployment and configuration](deploy.en.md). Connecting: [Connecting and using](usage.en.md).
